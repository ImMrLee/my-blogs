# recovery.dd（WinXP 磁盘）

检材：`recovery.dd`，1,073,741,824 字节，MBR 磁盘，磁盘签名 `0x2ce36279`
SHA256：`1bcb58a27e637e99a526799a0db42de6ea8b4a09dabf3764f140c512f947f8a2`
分析方式：只读解析镜像，按 MBR → EBR → NTFS 引导扇区 → MFT 记录 → 数据簇 的顺序逐层定位；下面的正文按题号 1→5 依次讲解。

## 答案速查

| 题 | 问题 | 答案 |
|---|---|---|
| 1 | 第二分区`classic/Toco Toucan.jpg` 起始簇 | 289,143 号簇（LCN，0 起算）／第 289,144 簇（1 起算） |
| 2 | 扩展分区首个 EBR 所在扇区 | 1,024,128（0xFA080） |
| 3 | 第三个分区总扇区数 | 612,801（0x959C1，约 299.2 MB） |
| 4 | 是否只有一个 FAT32 分区 | 是，仅 `NO NAME`（1,987,839 起，104,769 扇区） |
| 5 | 第三个分区 NTFS 的 `$MFT` 起始扇区 | 1,228,458（0x12BEAA） |

## 一、坐标系：先把整块盘想成一条编号传送带

镜像 1,073,741,824 B ÷ 512 B = **2,097,152 个扇区**，每个扇区一个编号（LBA），从 **0** 开始。所有位置最后都换算成这个编号：

```
字节偏移 = 扇区号 × 512
```

后面五题都是同一个动作：**找到某个结构的扇区号，再加减**。

---

## 二、题 1：答案藏在文件的 runlist 里 → 289,143

文件的元数据在 `$MFT` 里。`$MFT` 第 243 条记录（就是 `Toco Toucan.jpg`）含一个 `$DATA` 属性，非驻留（数据不在记录内，在别处），带一张簇地址表 runlist。原始字节：

```
32 e1 00 77 69 04 00 00
```

拆解：

- 首字节 `0x32`：高 4 位 `3` = 偏移占 3 字节，低 4 位 `2` = 长度占 2 字节；
- 长度 2 字节 `e1 00` → 225 簇（225 × 512 = 115,200 B，装得下 114,852 B 的文件）；
- 偏移 3 字节 `77 69 04` → 小端 `0x046977` = **289,143**；
- 末尾 `00` = 表结束。

第三个 NTFS 分区起点是 1,024,191 号扇区（推导见题 3），且该分区 1 簇 = 1 扇区（见题 5 的 BPB），因此这 289,143 簇在磁盘上的绝对扇区是 1,024,191 + 289,143。

所以“起始簇”不是猜的，是 runlist 第一个 run 的 LCN。再用 `dd` 看第 289,143 簇头 4 字节是否为 `FF D8 FF E0`（JPEG/JFIF），证明“这个簇确实存着这张图”。

```bash
dd if=recovery.dd bs=512 skip=$((1024191+289143)) count=1 status=none | xxd -l 8
# 00000000: ffd8 ffe0 0010 4a46  ......JF
```

## 三、题 2：MBR 只讲“入口在哪” → 1,024,128

MBR 的第 446 字节起，是 4 个 16 字节的格子，每格描述一个分区：

```
[状态 1][CHS 3][类型 1][CHS 3][起始 LBA 4][扇区数 4]
```

本案第二格（偏移 462）：

```
00 00 01 fe | 05 | 3f bf 06 | 80 a0 0f 00 | c0 4d 10 00
  状态/CHS   类型   CHS 结束    起始 LBA       扇区数
```

- 类型 `05` = **扩展分区**（它本身不是文件系统，只是一个“大盒子”）；
- 起始 LBA 小端读出 `0x000FA080` = **1,024,128**。

所以“第二分区是扩展分区、首个 EBR 在这个扇区”不是算出来的，是 **MBR 里写着的**。去 1,024,128 号扇区检查结尾是否为 `55 AA`（引导扇区签名），即可确认它是 EBR —— 这一步是验证，不是推算。

```bash
xxd -s 446 -l 32 recovery.dd
# 000001ce: 0000 01fe 053f bf06 80a0 0f00 c04d 1000
dd if=recovery.dd bs=512 skip=1024128 count=1 status=none | xxd -s 510 -l 2
# 000001fe: aa55
```

## 四、题 3：EBR 里写着它“多长” → 612,801

EBR 结构和 MBR 一样，但含义变了：

- **第一格 = 我这一个逻辑分区**，起点是“相对本 EBR 的偏移”；
- **第二格 = 下一个 EBR**，起点是“相对扩展分区开头”的偏移。

1,024,128 号扇区里的第一格：

```
00 00 01 fe | 07 | 3f bf 06 | 3f 00 00 00 | 41 a0 09 00
              NTFS            相对起点 63     扇区数
```

类型 `07`=NTFS，相对起点 `0x3F`=**63**，扇区数 `0x00095A41`=**612,801**。

于是分区真实起点 = 1,024,128 + 63 = **1,024,191**。

**为什么要加 63？** EBR 占着扩展分区的第 0 个扇区，逻辑分区从它后面第 63 个扇区才开始（老式磁道对齐习惯）。这也解释了火眼列出的起点为什么是 1,024,191 而不是 1,024,128。

```bash
dd if=recovery.dd bs=512 skip=1024128 count=1 status=none | xxd -s 446 -l 16
# ... 073f bf06 3f000000 41a00900
fdisk -l recovery.dd | grep dd5
# recovery.dd5  1024191 1636991  612801  299.2M  7 HPFS/NTFS/exFAT
```

## 五、题 4：类型码 + 全盘扫描 → 只有一个 FAT32

分区类型码 `0x0B`/`0x0C` 就是 FAT32。逐个分区读引导扇区、看 0x52 偏移是否为 `FAT32`，只有 1,987,839 命中；而 1,987,845 是它的**备份 BPB**（FAT32 规定第 6 扇区留一份），属同一个卷，不能算两个。

```bash
for s in 63 1024191 1637055 1887039 1987839; do
  printf '%8s: ' "$s"
  dd if=recovery.dd bs=512 skip=$s count=1 status=none | xxd -s 82 -l 8 -p
done
# 只有最后一行 4641543332202020 = "FAT32   "
```

## 六、题 5：NTFS 的“簇号”是相对分区算的 → 1,228,458

看 1,024,191 号扇区的 NTFS 引导扇区（BPB）：

| 偏移 | 字段 | 本案值 | 含义 |
|---|---|---|---|
| 0x0B | 每扇区字节数 | 512 | 一个扇区 512 B |
| 0x0D | 每簇扇区数 | 1 | **1 簇 = 1 扇区（关键）** |
| 0x30 | `$MFT` 起始簇 LCN | 204,267 | 主文件表从第 204,267 簇开始 |

NTFS 说“第 N 簇”，默认**从本分区第一个字节算起**，不是从磁盘第一个字节算起。所以：

```
绝对扇区 = 分区起点 + N × 每簇扇区数
1,024,191 + 204,267 × 1 = 1,228,458
```

去 1,228,458 号扇区看，开头正好是 `FILE` —— 这是 MFT 记录 0（`$MFT` 描述自己），验证通过。

**注意**：这题恰好“1 簇 = 1 扇区”，所以看起来像直接加；若每簇 8 扇区，必须乘 8。

```bash
dd if=recovery.dd bs=512 skip=1024191 count=1 status=none | xxd -s 48 -l 8
# 00000030: eb1d 0300 0000 0000    -> 0x00031DEB = 204267
echo $((1024191+204267))            # 1228458
dd if=recovery.dd bs=512 skip=1228458 count=1 status=none | xxd -l 4
# 00000000: 4649 4c45  FILE
```

## 七、三个最容易踩的坑

1. **LCN ≠ 绝对扇区**：NTFS 簇号相对分区起点，必须加分区起始扇区，还要乘每簇扇区数。
2. **0 起算 vs 1 起算**：写答案要说明“LCN 289,143”还是“第 289,144 簇”，否则差 1。
3. **分区表 vs 签名扫描**：`fdisk` 列出的与火眼列出的可能不一致，引用时注明来源。
